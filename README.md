## Project Overview
This project compares two search algorithms on the classic 3×3 8-puzzle and profiles them with real measurements instead of relying on theory alone:

- **Breadth-First Search (BFS)** – uninformed, optimal
- **A\* Search** with the **Manhattan-distance heuristic** – informed, optimal

It was developed across the SLE series (SLE-1 to SLE-4) and was built using an AI-augmented workflow. AI suggestions were reviewed, tested and checked before use (see `CONTRIBUTION_LOG.md`).

## Problem Setup
- Start state: `4 1 0 / 2 6 3 / 7 5 8`
- Goal state: `1 2 3 / 4 5 6 / 7 8 0` (0 = blank tile)
- The start state was generated by 22 random valid moves from the goal, so it is always solvable.
- A* uses `f(n) = g(n) + h(n)`, where `h(n)` is the sum of Manhattan distances of every tile from its goal position.

## Profiling Method
- Timing with Python `time.perf_counter()`
- Manual counter of nodes expanded (incremented every time a state is popped from the BFS queue / A* priority queue)
- Both algorithms run on the identical start and goal state; 3 runs per algorithm, averaged

## Results (SLE-2)
| Metric | BFS | A* (Manhattan) | Better |
|---|---|---|---|
| Avg. time (ms, 3 runs) | 0.3124 | 0.0613 | A* |
| Nodes expanded | 201 | 11 | A* |
| Solution depth | 8 (optimal) | 8 (optimal) | Tie |

A* was about 5× faster and expanded about 18× fewer nodes, with the same optimal 8-move solution.

## Architecture (SLE-3, C4 model)
The system is split into: state/grid builder, search engine (Frontier, Neighbours, Explored Set, Goal Test, Expansion Counter), profiler and report output. The Frontier is the only part that changes between algorithms (queue for BFS, priority queue for A*), which is why switching algorithms is a small change.

## Architecture Decision (SLE-4)
The ADR records the decision to use **A\* with Manhattan distance instead of BFS**. Rationale: far fewer expanded nodes, lower runtime, and still optimal because Manhattan distance is admissible. Trade-offs: it needs a good heuristic, has priority-queue overhead, and still uses a lot of memory on larger puzzles. See `SLE4_25UAM061.docx`.

## How to Run
```bash
python main.py
```
The program builds the puzzle, runs BFS and A* on the same states, and prints the results table (time, nodes expanded, solution depth).

## Limitations
- Results come from one start state and 3 runs, so they show a trend, not a general proof.
- Larger puzzles (e.g. 15-puzzle) would need a memory-efficient variant such as IDA*.
